# Read-back

**Status: COMPLETE 2026-10-01.** Every field a client sends through the gateway reads
back as sent, verified on k3s; stubs regenerate in CI. Decision:
→ [0028](../decisions/0028-what-a-client-sends-is-read-back.md), accepted.

**Goal:** A field a client sends is stored and read back as sent, and a generated stub
never drifts from its contract unseen.

**Why:** on 2026-10-01 three defects of one kind surfaced, each the first time
something read data back: the gateway's order stub, stale against its contract since at
least 2026-09-24; three order fields never stored; and the gateway dropping every zero
value from a reply. Unit tests passed through all three
(`docs/plans/2026-10-01-the-order-contract.md#results`).

## Global constraints

- A field found dropped is fixed test-first, at the layer that drops it.
- Go repository tests skip locally without their datastore and fail when `CI` is set.
- A check must be seen to fail before it is trusted.

---

### Task 1: the read-back gate

`deploy/scripts/gate-read-back.sh`, `make -C deploy k3s-gate-read-back`: a user signed
up then updated twice; an event created then updated in every field; its config
created then flipped in every field; an order. Each is read back through the gateway
and compared field by field, and every mismatch is reported, not only the first.

### Task 2: fix what it finds

One failing test per dropped field, at the layer that drops it, then the fix.

### Task 3: stubs cannot drift unseen

A CI job regenerates every Go and TS stub from `proto/` and fails on any difference.

### Task 4: stores read back in CI

Round-trip tests, every field, for the stores that have none: the waitroom's session,
inventory's ticket class and reservation, and the TS services' Prisma repositories.

### Task 5: verify on k3s, then record

Push; deploy; the read-back gate and the fast gates. Stop the box. 0028 with an
Outcome; this plan COMPLETE.

## Results

The gate found four defects on its first runs, each fixed test-first where the field
was dropped: event and sale updates unable to set a time of day (`cd456ea`), an event
update's venue never reaching event-svc (`dd97cef`), an event update ignoring
categories and erasing ward and district (`a2d90a1`), and an order item's price
carrying the line total (`41bbd37`). The table and the tests are in 0028's Outcome.

Task 3 landed as `39a10ff`, and Task 4 as `a2d90a1` (event-svc), `4441fc2` (waitroom
session), `f8bd566` (inventory ticket class) and `3c3c971` (payment).

Where the run departs from the tasks as written:
- user-svc has no repository suite. It writes its request straight to Prisma, so the
  suite would test Prisma; the gate reads its fields back end to end.
- Inventory's reservation needed none: the reserve and release suites already read it
  back from Postgres.
- `PaymentRepository.updateStatus` has no callers; the timestamps are written by the
  service and the webhook. It was left alone.
- The gate's first expectations were wrong twice: category ids are UUIDs, and an
  admitted session reads `READY`, as the contract names it.
